## ADDED Requirements

### Requirement: MingGua Engine Computes Hexagram From Accumulated Year
The MingGua engine SHALL compute the destiny hexagram (本卦) from a year input using the formula: accumulatedYear = year + epochBase, remainder = accumulatedYear % 64, hexagram = guaSequence[remainder == 0 ? 64 : remainder].

#### Scenario: Standard year produces correct hexagram
- **GIVEN** epochBase = 10153917 and the Tong Zong 64-hexagram sequence
- **WHEN** the engine calculates for year 2026
- **THEN** it SHALL produce the hexagram at position (10155943 % 64) in the sequence.

#### Scenario: Remainder zero maps to hexagram 64 (未济)
- **WHEN** accumulatedYear % 64 == 0
- **THEN** the engine SHALL select the 64th hexagram (未济), not index 0.

### Requirement: MingGua Uses Tong Zong Exclusive Hexagram Sequence
The hexagram sequence SHALL be the Tong Zong exclusive 64-hexagram order from 《太乙统宗宝鉴》卷十三, where position 43 is 姤 (NOT 夬 as in the standard Zhou Yi sequence).

#### Scenario: Position 43 is Gou not Guai
- **WHEN** the configured sequence is the Tong Zong sequence
- **THEN** guaSequence[42] SHALL equal '姤' and the sequence SHALL NOT contain '夬'.

#### Scenario: Sequence is configurable data
- **WHEN** a different hexagram sequence is provided in configuration
- **THEN** the engine SHALL use it without code changes.

### Requirement: MingGua Determines Moving Line By Yin-Yang Chen Rule
The moving line (动爻) SHALL be determined from the same remainder used for hexagram selection, with direction governed by Yin-Yang Chen: Yang Chen counts from bottom (初爻) up; Yin Chen counts from top (上爻) down.

#### Scenario: Yang Chen counts upward
- **GIVEN** a year whose GanZhi index is even (Yang Chen)
- **WHEN** the engine determines the moving line
- **THEN** it SHALL count from the first (bottom) line upward: position = ((remainder-1) % 6) + 1.

#### Scenario: Yin Chen counts downward
- **GIVEN** a year whose GanZhi index is odd (Yin Chen)
- **WHEN** the engine determines the moving line
- **THEN** it SHALL count from the sixth (top) line downward: position = 6 - ((remainder-1) % 6).

#### Scenario: Same remainder for hexagram and moving line
- **WHEN** computing both hexagram index and moving line
- **THEN** both SHALL use the same remainder value (no second modulo operation).

### Requirement: MingGua Generates Transformed Hexagram By Flipping Moving Line
The transformed hexagram (变卦) SHALL be generated by inverting only the moving line's Yin/Yang value in the original hexagram.

#### Scenario: Single line flip produces valid hexagram
- **GIVEN** a hexagram with moving line at position P
- **WHEN** the engine generates the transformed hexagram
- **THEN** exactly one line at position P SHALL be inverted, and the result SHALL map to a named hexagram in the sequence.

### Requirement: Destiny Engine Produces Twelve-Palace Chart From Birth Time
The Destiny engine SHALL accept a birth DateTime and produce a twelve-palace (十二人身宫) chart by: computing the hour-based Tai Yi chart (时计), extracting star-deity positions, and mapping them to twelve palaces according to configurable rules.

#### Scenario: Hour chart drives deity positions
- **WHEN** a birth time is provided
- **THEN** the engine SHALL compute the hour-basis Tai Yi chart (chartType=hour) using the configured school's epoch, and extract TaiYi, WenChang, ShiJi, host-count, and guest-count.

#### Scenario: Twelve palaces are configurable
- **WHEN** the destiny configuration specifies a palace mapping
- **THEN** each palace SHALL receive deities according to the mapping rules, not hardcoded logic.

### Requirement: Twelve-Palace Mapping Is Editable Data
Palace mappings (命宫 start point, sequence order, mapping rules) SHALL be stored as JSON configuration that users can edit, save, and switch between versions.

#### Scenario: User edits palace mapping
- **WHEN** a user modifies the twelve-palace mapping JSON and saves
- **THEN** subsequent calculations SHALL use the new mapping without code changes.

#### Scenario: Multiple mapping versions coexist
- **WHEN** two DestinyConfig documents exist with different palaceMappings
- **THEN** switching between them SHALL produce different twelve-palace results for the same input.

### Requirement: Contracts Extend repository-interface-taiyishenshu
MingGua and Destiny contracts (DTOs) and repository interfaces SHALL be defined in the `repository-interface-taiyishenshu` package, following the existing pattern (freezed DTOs + abstract repository classes).

#### Scenario: Interface package exports new contracts
- **WHEN** the interface package is imported
- **THEN** MingGuaConfigContract, MingGuaResultContract, DestinyConfigContract, DestinyResultContract, MingGuaRepository, and DestinyRepository SHALL be available.

### Requirement: MingGua And Destiny Are Independent Modules
The `lib/minggua/` and `lib/destiny/` directories SHALL NOT import from each other. Each module SHALL be independently testable and deployable.

#### Scenario: No cross-imports
- **WHEN** static analysis is run
- **THEN** no import statement in `lib/minggua/` SHALL reference `lib/destiny/` or vice versa.

### Requirement: MVP UI Sample Pages Demonstrate Results
The application SHALL include sample pages for both MingGua and Destiny that accept input and display computed results.

#### Scenario: MingGua sample shows hexagram
- **WHEN** a user enters a year on the MingGua sample page
- **THEN** the page SHALL display: accumulated year, remainder, original hexagram with line diagram, moving line position, and transformed hexagram.

#### Scenario: Destiny sample shows twelve palaces
- **WHEN** a user enters a birth datetime on the Destiny sample page
- **THEN** the page SHALL display: hour-chart parameters (ju number, dun type), host/guest counts, and a twelve-palace list with deity placements.
